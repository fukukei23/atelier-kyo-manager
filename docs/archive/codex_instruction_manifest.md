# Codex 指令書（atelier-kyo-manager 専用）

- **配置先**: `docs/codex_instruction_manifest.md`
- **更新日**: 2025-11-15
- **利用想定**: Codex / Claude / GPT 等のコーディング支援チャットを新規作成する際、最初のシステムメッセージまたはユーザーメッセージとして本書の内容を読み上げさせる。

---

## 0. 読み込み手順

1. VSCode Codex CLI / ブラウザ版など新しいチャットを開始する前に、このファイルを開いて全文コピー。
2. 可能であれば「System / Developer instructions」に貼り付ける。GUI がない場合はチャットの最初のユーザーメッセージとして投稿する。
3. ラン内で新たなプロンプトテキストが必要になったら、このファイルに追記しバージョン管理で共有する。
4. **会話言語**: Codex との会話は必ず日本語で行う（指示・応答ともに日本語で統一）。

---

## 1. 開発基本原則

1. **観測ベースの改善ループ**  
   - `run_orchestrator.py` などを実行して実サイトを観測し、得られた DOM・URL・ログに基づく提案のみを採用する。机上の推測修正は禁止。
2. **差分の自動保存**  
   - すべての修正は `codex_history/`（Codex Run Log、Git diff、自動取得アセット）や `exports/patches/` の成果物に紐づける。ログや diff を削除しない。
3. **自己進化サイクルの維持**  
   - Auto-Heal / SelfHealingAgent / GPTIntegration / CodeUpdateAgent の生成物を中心に検討。手動修正は最後の手段。
4. **環境を壊さない**  
   - `.env`, `instance/`, `logs/` などのユーザー固有ファイルを版管理に含めない。`.gitignore` に反すると判断したら即相談。

---

## 2. 作業ディレクトリと履歴管理

- ルート: `C:\Users\USER\tools\atelier-kyo-manager`（WSL からは `/mnt/c/Users/USER/tools/atelier-kyo-manager`）。
- Codex 履歴は `~/ .codex/sessions/` → `python tools/codex_history_manager.py` で `codex_history/` に同期。
  - 新ランの前後で `python3 tools/codex_history_manager.py` を実行し、Run LogとGit diffを確実に保存する。
  - 常駐させる場合は `python3 tools/codex_history_manager.py --watch --interval 60`。

---

## 3. コマンド / 実行方針

1. **優先タスク**: `run_orchestrator.py` による PLP 観測と `tools/apply_llm_proposal.py` 等の提案適用を高速に回す。
2. **記録義務**: 各タスクで実行したコマンドはログに必ず記録。特に `python` / `flask` / `pytest` 実行時は標準出力を要約して報告。
3. **テスト指針**:
   - 影響が設定ファイルのみなら `tests/test_llm_controller.py` を少なくとも 1 回。
   - 主要フロー変更時は `tests/test_app_smoke.py` を追加実行。
4. **外部アクセス**: ネットアクセスが必要な場合は必ずユーザーへ理由と手順を説明し、許可を得るまで待機。

---

## 4. コード編集スタイル

1. ASCII ベース。コメントは必要最低限で「なぜそれが必要か」を短く書く。
2. `apply_patch` をデフォルトの編集手段として使用し、ファイル丸ごと置き換えは避ける。
3. 既存の行末スペースやタブを不用意に変更しない。`.editorconfig` に従う。
4. 新規ファイルは冒頭に「ファイル名・更新日・目的」のメモを入れる（README, .gitignore 等に倣う）。
5. 既存ファイルを編集する際も、必要に応じてファイル名・レジストリ/パス・日付/時刻・バージョン・使用方法/操作すべきソフトを冒頭コメントに追記し、改訂履歴を残す。
6. モック/スタブ化したコード・未実装箇所はコメントや docstring で「スタブ」「仮実装」であると明示する。

---

## 5. レスポンスフォーマット

- CLI が自動整形する前提で以下を厳守:
  1. **最初に結論**: 変更内容のハイライトを 2〜3 行で。
  2. **詳細**: ファイル単位でどこを、なぜ変えたか。`path/to/file.py:42` のように行番号付きで。
  3. **テスト結果**: 実行したコマンドとステータス。未実行なら理由と推奨コマンド。
  4. **次のアクション**: 自然に想定されるステップがあれば明記。なければ省略可。

---

## 6. アラート・禁止事項

1. **ユーザー既存変更の上書き禁止**  
   - 既に編集済みのファイルを扱うときは `git diff` で差分を確認し、最小限の変更に留める。
2. **破壊的操作禁止**  
   - `git reset --hard`, `rm -rf` 等はユーザーからの明示指示がある場合のみ。
3. **秘密情報の扱い**  
   - `.env`, `forward2me.json` など機微情報はエディタで閲覧しても出力に含めない。
4. **冪等性**  
   - スクリプトやツールは再実行しても問題ない形にする（例: `mkdir -p`, `Path.mkdir(exist_ok=True)` を利用）。

## 9. Codex 社内規定（追加ルール）

1. **日本語コミュニケーション**  
   - Codex / Claude / GPT との対話は必ず日本語で行い、英語での指示・報告は避ける。
2. **コードメタ情報の明記**  
   - 新規・既存を問わず、編集したコードにはファイル名・レジストリ/配置場所・日付/日時・バージョン・推奨の使用方法や操作ソフトをコメントとして追加する。README `.gitignore` の記法を参考に、簡潔なヘッダを挿入する。
3. **スタブの可視化**  
   - スタブ化・モック化・未実装の関数/クラス/モジュールがある場合は、コメントや docstring で「スタブ」「未実装」と明記し、完成予定や依存関係も書き添える。
4. **遵守確認**  
   - 上記規定を守れない状況が発生した場合は、会話内でその理由と暫定対応を必ず報告する。
