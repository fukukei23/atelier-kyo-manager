## なぜこのバグが今まで生き延びたか（重要）

`docs/変更履歴.md` の 2026-07-13 エントリにこうある:

> 残34件（PriceIntegrityError系）を実測確認したところ、既に別セッションで全件解消済みと判明。
> 全2155件中 `2149 passed, 6 skipped, 0 failed`

**これは「テストが緑になった」ことの確認であって、「本番経路が動く」ことの確認ではなかった。**
実際にはテスト側が `PriceIntegrityError` を回避するよう書き換えられていただけで、
本番コードは当時から一度も動いていない。

`tests/test_sourcing_profitability_coverage.py:164-166` に、その判断が明記されている:

```python
# calculate_profitability 内部で PricingInput(price_source=UNKNOWN) を
# 構築して PriceIntegrityError を raise するため、テストではモック化。
```

→ **教訓**: 「テストが緑」を完了条件にしない。本番経路をモックなしで1回通すことを完了条件にする。
これは 2026-05-15 レビューの ISSUE-003（over-mocking 懸念）が現実化したケースでもある。

### 同じ構造の障害が別機能でも起きている（2026-08-13 追記）

本レビューの直後、main に `44badba`「Celery 配線修復（ワーカーがタスクを0件登録する機能停止級バグ）」が入った。
そのコミットメッセージにこうある:

> 従来テストは直接 import で関数を呼ぶだけで「ワーカーがタスクを知っているか」を検証していなかったのが
> 本バグの本質（**CI 2,149件が緑のまま気付かれなかった理由**）

**ISSUE-101/102 とまったく同じ構造**である。すなわち:

| 機能 | テストが検証していたもの | 実際に壊れていたもの |
|---|---|---|
| Celery（2026-08-13 修復済み） | 関数を直接 import して呼べること | ワーカーがタスクを登録できるか |
| 利益計算（ISSUE-101・未修正） | `calculate_pricing()` に正しい引数を渡せば動くこと | 呼び出し元が正しい引数を渡しているか |

いずれも「部品は動くがつなぎ目が切れている」型で、**単体テストでは原理的に検出できない**。
少なくとも2機能で発生している以上、単発の不具合ではなくテスト設計上のパターンとみなすべき。

**推奨**: ISSUE-101 の修正時に、テストを1件足すだけでなく
「HTTP経路 or ワーカー経路を1回通す結合テスト」をどこに置くかの方針を決めること。
Celery 側は `tests/test_celery_tasks.py` にレジストリ検証を置く形で解決しているので、
それに倣うのが自然。

### 第1ブロック（1〜2日）— pricing 層をまとめて

**ISSUE-101: `PriceIntegrityError` が正常系を全滅させている** 🔴 P0

`calculate_pricing()` は冒頭で `validate_sources()` を呼ぶが、呼び出し元6箇所が
`PricingInput` を price source 未設定（デフォルト `UNKNOWN`）で構築しているため必ず例外になる。

| 修正対象 | 到達経路 | 対応方針 |
|---|---|---|
| `app/models/order.py:83` | `POST /orders/new`, `/orders/<id>/edit` | `Order` に source カラム追加、暫定は `skip_source_validation=True` |
| `app/utils/sourcing_profitability.py:129` | `sourcing_pipeline.run_pipeline()` | `sourcing_input_schema` に source を必須追加 |
| `app/services/price_comparison_service.py:310` | 価格比較 | `PriceSource.BROWSER_VERIFIED` を明示 |
| `app/services/brand_price_service.py:230` | ブランド価格調査 | 同上 |
| `app/services/price_monitor_service.py:371` | `_update_profitability()` | 同上 |
| `app/agents/profitability_agent.py:116` | 収益性エージェント | 同上 |

**恒久対策**: `PricingInput.purchase_price_source` / `selling_price_source` のデフォルト値
`UNKNOWN` を廃止し必須引数化する。そうすれば同種の欠落が型チェックで露見する。

**完了条件**: 上記6経路すべてについて、**モックなしの**正常系テストが green。
加えて `POST /orders/new` が 302 を返し DB に1件入る smoke test を追加すること。

### → `01_DECISIONS/atelier-kyo-manager/2026-08-12_包括レビューとPriceIntegrityError配線漏れの発見.md`

記録すべき判断理由と技術的詳細:

- **発見の経緯**: テスト2,149件が緑・カバレッジ46%・ruff green という健全に見える状態で、
  実際にコードを実行したところ本番経路6つが例外で停止していた
- **根本原因**: `PricingInput` の price source がデフォルト `UNKNOWN` で、
  呼び出し側が明示しなくてもコンパイル/型チェックを通過してしまう設計
- **設計判断**: `PriceSource` による出所トラッキング自体は過去の失敗（キーワード推測で
  ¥13,000〜25,000 過大評価）への対策として妥当。**欠陥ではなく配線漏れ**なので、
  安全装置を緩めるのではなくデフォルト値を廃止して必須引数化する方向で直す
- **プロセスの教訓**: 2026-07-13 の「PriceIntegrityError 系全件解消済み」判定は
  テスト緑のみの確認だった。今後は本番経路をモックなしで通すことを完了条件にする
- **2026-05-15 レビュー ISSUE-003 との関連**: over-mocking 懸念が具体的実害として顕在化した実例
